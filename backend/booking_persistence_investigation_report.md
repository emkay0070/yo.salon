# Booking Persistence Investigation Report

## Issue Summary
**Reported:** `POST /api/v1/bookings/with-account` returned HTTP 422 with `{"message":"Undefined array key \"customer\""}` when email was omitted, yet the booking and customer appeared in the owner's dashboard.

**Investigation Date:** October 9, 2026

## Executive Summary

**CRITICAL FINDING:** The reported error message `"Undefined array key \"customer\""` does **not exist** in the booking creation code path. Extensive code search found no location where this specific error would be raised during booking creation.

The actual error found in application logs is a **different error**: `TypeError: Cannot access offset of type array on array` occurring in `CustomerSpecialistService.php:35`.

**HYPOTHESIS:** The reported error message may be from a different context (e.g., payment verification, webhook processing) or may have been misreported. The actual failure sequence cannot be determined without the exact browser Network log with timestamp and request ID.

## 6. Verified Event Sequence (Based on Code Analysis)

### 6.1 Normal Successful Flow

1. **Request Validation** (BookingController::storeWithAccount)
   - Validates all required fields
   - `customer_email` is optional, so omission passes validation

2. **Idempotency Check** (BookingOrchestrator::reserveAndBook)
   - Checks for existing booking with same `idempotency_key`
   - If found, returns existing booking immediately

3. **Cache Lock Acquisition** (BookingOrchestrator::reserveAndBook)
   - Acquires distributed lock on slot
   - Prevents concurrent bookings for same time

4. **Transaction Start** (BookingOrchestrator::reserveAndBook)
   - Begins DB transaction

5. **Customer Resolution** (BookingService::createBookingWithAccount)
   - `Customer::firstOrCreate(['phone' => $data['customer_phone']])`
   - Creates new customer if phone doesn't exist
   - Returns existing customer if phone matches

6. **Customer-Provider Relationship** (BookingService::createBookingWithAccount)
   - Checks if customer has relationship with provider
   - Creates `customer_providers` row if missing

7. **Booking Creation** (BookingService::createBookingWithAccount)
   - Creates `bookings` row
   - Creates `booking_services` rows with timing

8. **Customer-Specialist Relationship** (BookingService::createBookingWithAccount)
   - Calls `CustomerSpecialistService::trackRelationshipFromBooking`
   - Creates or updates `customer_specialists` row

9. **Portal Account Creation** (BookingService::createBookingWithAccount)
   - If `create_account=true`, creates portal account

10. **Payment Initialization** (BookingService::createBookingWithAccount)
    - If deposit required and payment method provided, initializes payment

11. **Transaction Commit**
    - All changes committed atomically

12. **Cache Lock Release** (BookingOrchestrator::reserveAndBook)
    - Releases distributed lock in `finally` block

13. **Response** (BookingController::storeWithAccount)
    - Returns HTTP 201 with booking, customer, portal_account details

### 6.2 Failure Flow (Based on Actual Log Error)

1. Steps 1-7 proceed normally

2. **Step 8: Customer-Specialist Relationship**
   - `CustomerSpecialistService::trackRelationshipFromBooking` called
   - At line 35, `$relationship->update([...])` throws TypeError
   - `$relationship` is array instead of Eloquent model

3. **Transaction Rollback**
   - Exception propagates through transaction
   - All changes (customer, customer_providers, booking) rolled back
   - Database returns to pre-request state

4. **Cache Lock Release**
   - `finally` block releases lock

5. **Exception Handler** (BookingController::storeWithAccount)
   - Catches exception at line 569
   - Returns HTTP 422 with exception message

**Expected Result:** No booking or customer should persist in database.

## 7. Hypotheses for Observed UI Behavior

### 7.1 Hypothesis 1: Different Request Created the Booking

**Explanation:** The booking that appeared in the dashboard was created by a DIFFERENT request that succeeded, not the one that returned HTTP 422.

**Evidence Needed:**
- Browser Network log with timestamps for ALL `/bookings/with-account` requests
- Database query to find booking creation timestamp
- Correlation of request timestamp with booking creation time

**Plausibility:** HIGH - This is the most likely explanation if the transaction rolled back correctly.

### 7.2 Hypothesis 2: Transaction Did Not Roll Back

**Explanation:** The transaction failed to roll back due to database configuration or connection issue, leaving partial data.

**Evidence Needed:**
- Database configuration for autocommit
- Laravel database transaction settings
- Check if booking has `customer_providers` relationship

**Plausibility:** LOW - Laravel's DB transactions are reliable. Partial commits are extremely rare.

### 7.3 Hypothesis 3: Error Message is Misreported

**Explanation:** The actual error was different (e.g., the TypeError from logs), and the "Undefined array key customer" error is from a different context or was misremembered.

**Evidence Needed:**
- Exact browser Network log with response body
- Application logs around the reported timestamp
- Request ID or correlation ID

**Plausibility:** HIGH - The reported error does not exist in the code.

### 7.4 Hypothesis 4: Frontend Cache or Stale UI

**Explanation:** The booking was from a previous successful request, and the UI showed stale data.

**Evidence Needed:**
- Frontend caching configuration
- UI refresh behavior
- Whether dashboard was refreshed after the error

**Plausibility:** MEDIUM - Possible if frontend caches booking data.

### 7.5 Hypothesis 5: Customer Existed Before Request

**Explanation:** The customer already existed in the database from a previous interaction, and only the booking creation failed.

**Evidence Needed:**
- Customer creation timestamp
- Previous bookings for this customer
- Whether customer appeared in Clients list BEFORE the failed request

**Plausibility:** MEDIUM - If customer existed, they would appear in Clients list regardless of booking success.
